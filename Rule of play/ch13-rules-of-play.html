Rules of Play  ·  Unit Two: Rules  ·  Chapter 13

Rules of Digital Games

Code enforces rules automatically — but the three-level model still applies. What changes, and what stays the same.

Code Is Not Rules

The most important opening move this chapter makes is a distinction that is easy to miss: code is not the same thing as rules. Code is the mechanism by which rules are enforced in digital games — but the code itself is not the rules. The rules of a digital game exist at the same three levels as the rules of any game (constituative, operational, implicit), and code is simply a more powerful enforcement mechanism than a physical board or a referee.

In a non-digital game, players enforce the rules themselves. In a digital game, the software enforces them automatically. A player cannot make an illegal Chess move in a digital Chess program — not because the code prohibits the rule, but because the code makes it physically impossible to enact. The rules still exist at the logical level; the code simply makes violations structurally impossible rather than merely prohibited.

This distinction matters for designers. Thinking of code as the rules conflates two different things: the logical structure of the game (the rules) and the technical implementation of that structure (the code). A designer who only thinks about code is working at the implementation level, not the rule level. Game design requires reasoning at both.

The Six Qualities Still Apply

The six qualities of rules identified in Chapter 11 — limiting action, explicit and unambiguous, shared by all players, fixed during play, binding, and repeatable — apply to digital games exactly as they apply to non-digital games. Code does not change what rules are; it changes how they are enforced and made available to players.

In some ways, digital implementation makes the six qualities more reliable: code ensures rules are consistently applied, eliminates ambiguity (the computer cannot misread a rule), and makes them automatically shared and fixed. But this does not mean digital rules are therefore simple or transparent. A digital game's ruleset can be extraordinarily complex, and its constituative structure — the underlying logic — may be just as opaque to players as 3-to-15's magic square structure.

Tetris: A Full Ruleset

To make the rules of a digital game concrete, the chapter walks through the complete operational rules of Tetris. This is valuable because Tetris feels simple — and in one sense it is — but writing out all its rules reveals substantial complexity:

  1. The playing field is a rectangle, 10 units wide and 20 units tall.
  2. Tetrominoes (geometric pieces composed of four square blocks) fall from the top of the field.
  3. Seven tetromino shapes exist: I, O, T, S, Z, J, L.
  4. The player can move the falling tetromino left or right, and rotate it clockwise or counterclockwise.
  5. The player can also accelerate the tetromino's descent.
  6. When a tetromino reaches the bottom or lands on another piece, it locks in place.
  7. When a horizontal row of the field is completely filled, that row is cleared and all rows above it drop down by one.
  8. Clearing multiple rows simultaneously scores bonus points.
  9. A new tetromino appears at the top after each lock.
  10. The next tetromino to appear is displayed in a preview area.
  11. The falling speed increases over time.
  12. The game ends when a locked piece reaches the top of the field.

Twelve rules. And yet the full constituative structure of Tetris — the mathematical space of all possible configurations, the optimal clearing strategies, the way piece types interact with field states — is vastly richer than these twelve operational rules suggest. The operational layer is the doorway; the constituative structure is the vast space behind it.

Rules and Not-Rules

A key analytical move this chapter makes is distinguishing between what is a rule and what is not. Digital games embed enormous amounts of design that is not rule — aesthetic choices, presentation decisions, stylistic elements — and confusing these with rules leads to analytical errors.

Rules (Formal Structure) Conditions, constraints, and logical relationships that determine what is possible in the game. Removing or changing these changes what the game is. They exist at the constituative or operational level.
Not-Rules (Aesthetic / Presentational) Visual design, sound effects, narrative framing, color palette, character appearance, animation style. Changing these changes how the game looks and feels but does not change the game's formal structure.

Three examples from the book illustrate where this line falls:

Game and Watch Gallery

Nintendo's Game and Watch Gallery released Classic and Modern versions of the same mini-games. The Classic version used blocky monochrome graphics; the Modern version featured full-color Mario characters. The formal rules were identical — same move sets, same win conditions, same scoring. Yet players experienced them as different games. The aesthetic layer is not rules, but it profoundly shapes experience. This is a design opportunity: the same rule structure can produce very different experiential registers depending on presentation.

Berzerk and Sprite Size

The arcade game Berzerk features robot enemies that pursue the player through a maze. The robots' visual size on screen is not a rule — it is an aesthetic parameter. But in practice, a larger sprite makes the robots feel more threatening, affects how players read the play space, and alters gameplay feel without altering any formal rule. Aesthetic choices have rule-like effects on experience even when they are not themselves rules.

Thief: The Dark Project

The stealth game Thief uses lighting as a core gameplay element: shadowed areas make the player character harder for enemies to detect. The rule is about detection probability — a formal, quantified relationship between light levels and enemy perception. The visual presentation of shadows is the aesthetic expression of that rule. Understanding the rule (detection probability) is separate from understanding its aesthetic expression (shadows). A designer must understand both levels and their relationship.

Wheels Within Wheels: Software Layers

Digital games exist within a nested hierarchy of software systems. The game's rules are implemented in code, but that code runs on top of an operating system, which runs on hardware, which has its own physics. The authors describe this as "wheels within wheels" — each layer enforces constraints on the layers above it.

Hardware
The physical computer: processor speed, memory, display resolution. Sets absolute physical limits on what is computable and displayable.
Operating System
Manages hardware resources, handles input and output, enforces memory boundaries. The game code runs within the constraints the OS establishes.
Game Engine
Provides physics simulation, rendering pipeline, audio management, input handling. The specific game logic runs on top of the engine's substrate.
Game Code
The rules-implementing layer — the logic that defines states, allowed transitions, winning conditions, and the formal structure of the game.
Player Interaction
The interface through which players act on the game system. Controller inputs, mouse clicks, and keyboard events are translated into game actions.

This layered view explains why digital game design is complex even when rules are "simple." The same formal rule can behave differently depending on how it is implemented in code, how the engine handles edge cases, and how input latency or rendering performance affects the player's ability to execute their intentions.

The Three-Level Model Applied to Digital Tic-Tac-Toe

To crystallize the three-level framework in the digital context, the chapter applies it to a digital version of Tic-Tac-Toe:

Constituative Rules

The abstract logical structure — the magic square, the two-player zero-sum game on a 3×3 grid — is identical to non-digital Tic-Tac-Toe. Digitization does not change the constituative level. The game system consists of discrete internal events: move selections and state transitions, defined as mathematical operations on a 3×3 matrix of values.

Operational Rules

The operational layer expands to include the digital interface. The authors enumerate six operational rules for digital Tic-Tac-Toe:

  1. Click on an empty square to place your mark.
  2. The computer alternates turns automatically.
  3. Illegal moves (clicking an occupied square) are prevented by the interface.
  4. The game detects win conditions automatically after each move.
  5. When a win or draw is detected, the game displays a result screen.
  6. Players can start a new game by clicking "Play Again."

The operational layer now includes I/O operations and player interaction patterns that have no equivalent in the physical game — the game enforces rules automatically rather than requiring player self-policing.

Implicit Rules

The implicit rules shift with the platform. Conventions about how digital games "should" work — cursor behavior, button feedback, expected sound cues, the meaning of a "Play Again" prompt — are implicit norms players bring from their broader digital game experience. These conventions are not in the code, but they shape player expectations powerfully.

Crucially, violating platform conventions — making a game that behaves in unexpected ways for its medium — can be a powerful design strategy. Questioning implicit rules is a source of innovation.

Why Rules? The Designer's Answer

The chapter closes with a return to first principles: why should game designers care about rules in this analytical depth? The answer is that understanding the formal structure of a game is the prerequisite for designing it well.

A designer who cannot distinguish between a game's constituative structure and its operational presentation cannot make principled choices about either. A designer who cannot identify the implicit rules of their platform cannot recognize which conventions to honor and which to break. The three-level model is not academic scaffolding — it is a practical tool for understanding what a game is, what it is doing, and what changes are possible.

Identifying the rules of a game — at all three levels — is one of the most important things a game designer can do. You cannot redesign what you cannot see, and the formal structure of a game is invisible unless you look for it deliberately.

Chapter Summary

  • Code is not rules. Code is the enforcement mechanism for rules in digital games. The rules themselves exist at the logical level; code makes rule violations structurally impossible rather than merely prohibited.
  • The six qualities of rules apply to digital games exactly as to non-digital games. Digital implementation makes some qualities (consistency, unambiguity) more reliable but does not change what rules are.
  • Tetris demonstrates that even a "simple" digital game has a complete and non-trivial ruleset at the operational level — twelve rules — with a much richer constituative structure beneath.
  • Rules vs. not-rules: Visual design, sound, narrative, and aesthetics are not rules — they shape experience but do not define formal structure. The distinction matters for analysis and design.
  • Digital games exist within layered software systems (hardware, OS, engine, game code, player interface). Understanding these layers explains why digital game behavior can be complex even when formal rules are simple.
  • Implicit rules in digital games include platform conventions — expectations about how games should behave based on broader digital experience. Violating these conventions deliberately is a design opportunity.
  • The three-level model is a practical design tool, not just academic analysis — it reveals what is changeable, what is fixed, and what is invisible in a game's structure.
