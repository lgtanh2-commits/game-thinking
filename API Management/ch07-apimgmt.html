Bảo Mật API

OAuth 2.0, JWT, mTLS, OWASP API Top 10 và chiến lược bảo vệ API toàn diện

Tại Sao Bảo Mật API Là Ưu Tiên Số Một?

API là cửa sổ vào dữ liệu và dịch vụ doanh nghiệp. Không giống website (người dùng thấy giao diện), API trực tiếp expose business logic và dữ liệu nhạy cảm qua internet. Một API kém bảo mật có thể dẫn đến: lộ dữ liệu khách hàng, gian lận tài chính, mất kiểm soát hệ thống, thiệt hại danh tiếng và pháp lý.

Gartner dự báo rằng đến năm 2025, API sẽ trở thành vector tấn công phổ biến nhất, vượt qua cả web application. Đây không phải cường điệu — Salt Security API Security Report 2023 cho thấy 94% tổ chức đã trải qua sự cố bảo mật API trong 12 tháng qua.

Ba Tầng Bảo Mật API

🔑

Tầng 1: Xác Thực (Authentication) — "Bạn là ai?"

Xác minh danh tính của caller — người dùng hay ứng dụng. API key, OAuth 2.0 access token, JWT, mutual TLS certificate. Không có authn, không thể biết ai đang gọi API.

🔓

Tầng 2: Phân Quyền (Authorization) — "Bạn được làm gì?"

Sau khi xác minh danh tính, kiểm tra quyền truy cập tài nguyên cụ thể. Role-based (RBAC), attribute-based (ABAC), scope-based (OAuth). Đảm bảo user A không đọc được data của user B.

🛡️

Tầng 3: Bảo Vệ & Phát Hiện — "Ngăn chặn lạm dụng"

Rate limiting, threat detection, input validation, data masking, audit logging. Phát hiện và ngăn chặn tấn công kể cả từ client đã xác thực hợp lệ.

API Key — Đơn Giản Nhưng Hữu Hạn

API key là chuỗi token dài, ngẫu nhiên được cấp cho mỗi app/developer. App gửi key trong header (Authorization: ApiKey abc123 hoặc X-API-Key: abc123) hoặc query param (?api_key=abc123).

Phù hợp: xác thực server-to-server, developer portal access, public API với rate limiting đơn giản.

Hạn chế: key không có expiry mặc định (risk nếu bị leak), không mang thông tin user (không biết key thuộc về ai trong một org), không phù hợp cho user-facing app (key dễ bị expose trong JavaScript).

OAuth 2.0 — Chuẩn Phân Quyền Hiện Đại

OAuth 2.0 là framework phân quyền — cho phép ứng dụng truy cập tài nguyên của user mà không cần user chia sẻ mật khẩu. OAuth 2.0 định nghĩa bốn roles:

  • Resource Owner — user sở hữu dữ liệu
  • Client — ứng dụng muốn truy cập dữ liệu
  • Authorization Server — cấp access token (Google, Facebook, Okta, Auth0...)
  • Resource Server — API server chứa dữ liệu được bảo vệ

OAuth 2.0 Authorization Code Flow (cho Web App)

Luồng phổ biến nhất — dùng khi có user interaction

1App redirect user đến Authorization Server: GET /authorize?response_type=code&client_id=...&scope=read:orders&redirect_uri=...
2User đăng nhập và chấp thuận quyền (consent screen). Authorization Server sinh authorization code ngắn hạn (vài giây).
3Authorization Server redirect về app với code: GET /callback?code=AUTH_CODE
4App đổi code lấy access token: POST /token với client_secret. Bước này xảy ra server-side — client_secret không bao giờ expose ra browser.
5App dùng access token gọi API: Authorization: Bearer {access_token}
6API server validate token (với Authorization Server hoặc local nếu dùng JWT), trả về data.

OAuth 2.0 Grants Khác

  • Client Credentials — server-to-server, không có user. App dùng client_id + client_secret để lấy token trực tiếp. Phổ biến nhất cho machine-to-machine API calls.
  • PKCE (Proof Key for Code Exchange) — Authorization Code Flow cho mobile/SPA không thể giữ bí mật client_secret. Thay bằng code_verifier/code_challenge.
  • Device Authorization — cho thiết bị không có browser (smart TV, IoT). User xác thực trên thiết bị khác.

JWT — JSON Web Token

JWT là định dạng token tự chứa (self-contained) — mang đủ thông tin để Resource Server xác minh mà không cần gọi Authorization Server mỗi lần. Cấu trúc: HEADER.PAYLOAD.SIGNATURE

// Header (Base64URL encoded) { "alg": "RS256", "typ": "JWT" } // Payload (Base64URL encoded) { "sub": "user-123", // Subject (user ID) "iss": "https://auth.example.com", // Issuer "aud": "api.example.com", // Audience (API resource server) "exp": 1697400000, // Expiration (Unix timestamp) "iat": 1697396400, // Issued At "scope": "read:orders write:orders", "roles": ["admin"] } // Signature (RSA/HMAC over header.payload) RSASHA256(base64(header) + "." + base64(payload), private_key)

Resource Server verify JWT bằng public key của Authorization Server — không cần network call. Nhanh và có thể scale. Nhược điểm: JWT không thể revoke trước khi expire (dùng short expiry + refresh token để giảm risk).

OpenID Connect (OIDC)

OIDC là lớp identity trên OAuth 2.0. OAuth chỉ xử lý authorization (quyền truy cập), còn OIDC thêm authentication — trả về ID Token (JWT chứa thông tin user: name, email, profile). OIDC là chuẩn "Sign In with Google/Facebook/Microsoft" mà mọi web app đều dùng.

Mutual TLS (mTLS) — Bảo Mật Cấp Service

TLS thông thường: chỉ client verify certificate của server. mTLS: cả hai bên verify certificate của nhau. Thường dùng cho:

  • Service-to-service communication trong microservices (service mesh như Istio dùng mTLS mặc định)
  • High-security B2B API (fintech, banking) — partner phải có certificate hợp lệ mới gọi được API
  • Bổ sung cho OAuth trong zero-trust architecture (Sender-Constrained Token / DPoP)

OWASP API Security Top 10 — 2023

OWASP (Open Web Application Security Project) công bố danh sách 10 rủi ro bảo mật API phổ biến nhất. Đây là checklist bắt buộc cho mọi API team:

API1: Broken Object Level Authorization (BOLA)

API không kiểm tra user có quyền truy cập object ID cụ thể không. User A gửi GET /orders/999 và nhận được order của User B nếu API chỉ verify authentication mà không verify authorization theo object.

✅ Mitigation: Luôn validate quyền sở hữu object theo user đang gọi API. Không dùng sequential ID — dùng UUID để ngăn enumeration.

API2: Broken Authentication

Cơ chế xác thực yếu: không có brute-force protection, credential stuffing, token không expire, JWT với "none" algorithm được chấp nhận.

✅ Mitigation: Dùng short-lived token, refresh token rotation, account lockout, MFA, không implement auth tự làm — dùng IdP chuẩn.

API3: Broken Object Property Level Authorization

API trả về hoặc cho phép cập nhật nhiều field hơn user được phép — "mass assignment" hay "excessive data exposure". User có thể đọc trường isAdmin hoặc tệ hơn, set nó thành true.

✅ Mitigation: Dùng allowlist field (whitelist), không trả về model database trực tiếp, phân biệt rõ read vs write permissions theo từng field.

API4: Unrestricted Resource Consumption

Không có rate limiting, quota hay cost control. Attacker khai thác API để gây DoS, tốn chi phí cloud (API calls tốn tiền), hay extract toàn bộ database qua pagination.

✅ Mitigation: Rate limiting, consumption quota, spike arrest, max page size, timeout cho API call. Monitor và alert khi usage bất thường.

API5: Broken Function Level Authorization

API expose admin/privileged endpoints mà regular user có thể gọi nếu biết URL. Ví dụ: DELETE /admin/users/{id} không kiểm tra role admin.

✅ Mitigation: Default deny — mọi endpoint mặc định require authorization. Tách admin và user API, kiểm tra role ở mọi endpoint.

API6: Unrestricted Access to Sensitive Business Flows

Không có rate limiting nghiệp vụ. Bot có thể mua toàn bộ hàng giới hạn, gửi spam OTP, enumerate tài khoản qua "forgot password" response khác nhau.

✅ Mitigation: Device fingerprinting, CAPTCHA, velocity checking, business rate limiting tách biệt với technical rate limiting.

API7: Server-Side Request Forgery (SSRF)

API nhận URL từ client và gọi URL đó — attacker có thể chỉ vào internal service (http://169.254.169.254 để lấy AWS metadata, internal databases).

✅ Mitigation: Whitelist allowed URL patterns và domains, không resolve internal IP từ URL được user cung cấp.

API8: Security Misconfiguration

TLS version cũ, không có security headers, CORS quá rộng (Access-Control-Allow-Origin: * cho authenticated API), stack trace lộ trong error response, debug endpoint không tắt ở production.

✅ Mitigation: Security hardening checklist, automated security scanning trong CI/CD, regular security audit.

API9: Improper Inventory Management

Không biết tất cả API đang có — shadow API (chạy không có ai biết), deprecated API chưa tắt, API với version cũ không được bảo vệ như version mới.

✅ Mitigation: API catalog/registry đầy đủ, API discovery tool, lifecycle governance, tắt API không dùng.

API10: Unsafe Consumption of APIs

API của bạn consume third-party API mà không validate, dẫn đến inject attack khi third-party trả dữ liệu độc hại. Supply chain risk.

✅ Mitigation: Validate và sanitize dữ liệu từ mọi external API. Đừng tin tưởng blindly kể cả trusted partner.
