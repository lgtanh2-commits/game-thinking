Quản Lý Phiên Bản API

Chiến lược versioning để API tiến hóa mà không phá vỡ ứng dụng hiện có

Tại Sao API Cần Versioning?

API là hợp đồng giữa provider và consumer. Khi hợp đồng thay đổi theo cách không tương thích ngược (breaking change), mọi consumer đang dùng API cũ sẽ bị ảnh hưởng — có thể dẫn đến lỗi production nghiêm trọng.

Thực tế, API phải tiến hóa liên tục: thêm tính năng mới, cải thiện thiết kế, đáp ứng yêu cầu bảo mật mới, loại bỏ kỹ thuật nợ. Versioning cho phép API thay đổi mà vẫn đảm bảo backward compatibility — consumer hiện tại tiếp tục hoạt động bình thường trong khi consumer mới được khuyến khích dùng phiên bản mới hơn.

Breaking Changes vs Non-Breaking Changes

🚨 Breaking Changes — Cần Tăng Version

  • Xóa endpoint hoặc HTTP method
  • Đổi tên field bắt buộc trong request/response
  • Thay đổi kiểu dữ liệu (string → integer)
  • Thêm field bắt buộc mới vào request
  • Thay đổi format URL (đổi tên path parameter)
  • Thay đổi authentication mechanism
  • Thay đổi semantic của endpoint (behavior khác)
  • Xóa giá trị enum đang được dùng

✅ Non-Breaking Changes — Không Cần Version Mới

  • Thêm endpoint mới
  • Thêm field mới tùy chọn vào response
  • Thêm field mới tùy chọn vào request
  • Thêm giá trị enum mới
  • Bug fix (behavior đúng hơn, không thay đổi contract)
  • Cải thiện performance, không thay đổi giao diện
  • Thêm optional query parameter
  • Cải thiện tài liệu

Semantic Versioning (SemVer)

MAJOR.MINOR.PATCH — Ví dụ: 2.3.1

2MAJOR
Breaking changes
.
3MINOR
New features,
backward-compat
.
1PATCH
Bug fixes,
backward-compat

Trong API management, thường chỉ expose MAJOR version trong public URL/header (v1, v2) — consumer không cần biết minor và patch version vì chúng backward-compatible. MINOR/PATCH được manage nội bộ.

Các Chiến Lược Versioning

1. URI Path Versioning (Phổ biến nhất)

GET https://api.example.com/v1/orders
GET https://api.example.com/v2/orders

Version được đặt trực tiếp trong URL path. Cách rõ ràng và dễ dùng nhất — developer thấy ngay đang dùng version nào. Dễ cache, dễ route ở gateway, dễ test bằng browser.

Nhược điểm: URL không "RESTful thuần túy" (version không phải là phần của resource), cần cập nhật toàn bộ URL khi upgrade. Đây là trade-off được hầu hết API thực tế chấp nhận.

Được sử dụng bởi: Stripe API, Twilio, GitHub API v3/v4.

2. Header Versioning

GET https://api.example.com/orders
API-Version: 2023-10-01

Accept: application/vnd.example.v2+json

Version được truyền qua HTTP header — hoặc custom header (API-Version, X-API-Version) hoặc Accept header với media type versioning. URL giữ "sạch" không chứa version.

Nhược điểm: Khó test bằng browser (cần tool như Postman/curl), không cached mặc định bởi browser, ít trực quan hơn với developer mới.

Được sử dụng bởi: Microsoft Graph API (dùng API-Version header với date-based versioning như 2023-01-01), Stripe cũng hỗ trợ header versioning song song.

3. Query Parameter Versioning

GET https://api.example.com/orders?version=2
GET https://api.example.com/orders?api-version=2023-10-01

Version trong query parameter. Linh hoạt, không thay đổi URL path, dễ test. Tuy nhiên, ít rõ ràng hơn path versioning và thường bị coi là "last resort".

Được sử dụng bởi: Azure REST API (api-version parameter), Google Cloud APIs.

4. Date-based Versioning

GET https://api.example.com/orders
Stripe-Version: 2023-10-16

Thay vì số version, dùng ngày để xác định "snapshot" của API. Mọi breaking change được đưa vào API với ngày mới. Consumer có thể pin vào ngày cụ thể để đảm bảo behavior không thay đổi.

Stripe là ví dụ điển hình — developer có thể dùng Stripe API hành xử như ngày 2019-05-16 cho đến khi họ sẵn sàng migrate.

Vòng Đời Phiên Bản API

Mỗi version API trải qua các giai đoạn:

Alpha
(nội bộ)
Beta
(early access)
GA
(stable)
Deprecated
(warning)
Sunset
(removed)
  • Alpha — chỉ dùng nội bộ, có thể thay đổi bất cứ lúc nào
  • Beta — mở cho early adopter, có thể có breaking change nhưng sẽ thông báo trước
  • GA (Generally Available) — stable, backward-compatible, có SLA. Đây là version production.
  • Deprecated — vẫn hoạt động nhưng sẽ bị xóa trong tương lai. Response header Deprecation và Sunset thông báo cho client.
  • Sunset (Retired) — version bị xóa, trả về 410 Gone hoặc redirect đến version mới

Chiến Lược Deprecation Hiệu Quả

Deprecation không phải là tắt API — đó là quá trình có kế hoạch với timeline rõ ràng:

  • Thông báo sớm — ít nhất 6-12 tháng trước khi sunset, càng sớm càng tốt
  • Thông báo nhiều kênh — email đến developer đăng ký, developer portal, response header, changelog
  • Response headers chuẩn:
    • Deprecation: Thu, 01 Jan 2025 00:00:00 GMT — ngày deprecated
    • Sunset: Thu, 01 Jul 2025 00:00:00 GMT — ngày bị xóa hoàn toàn
    • Link: </v2/orders>; rel="successor-version" — link đến version mới
  • Migration guide đầy đủ — hướng dẫn chi tiết cách chuyển từ v1 sang v2, kèm code sample
  • Support song song — duy trì cả hai version trong giai đoạn transition
  • Theo dõi usage — identify consumer vẫn dùng version cũ để liên hệ trực tiếp hỗ trợ migration
Quy tắc vàng: Đừng bao giờ tắt API đột ngột. Mỗi lần API bị tắt không báo trước là một lần mất đi trust của developer community — thứ rất khó xây dựng lại.
