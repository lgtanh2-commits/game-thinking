Thiết Kế Giao Diện RESTful

Nguyên tắc thiết kế REST API chuẩn: resource, HTTP method, status code và request/response

REST Là Gì?

REST (Representational State Transfer) là phong cách kiến trúc được Roy Fielding định nghĩa trong luận án tiến sĩ năm 2000. REST không phải chuẩn hay giao thức — đó là tập hợp ràng buộc kiến trúc hướng dẫn thiết kế hệ thống phân tán qua HTTP. API tuân thủ REST được gọi là RESTful API.

RESTful API được ưa chuộng nhất cho API hiện đại vì tính đơn giản, nhẹ, dễ sử dụng và khả năng mở rộng cao. JSON là định dạng dữ liệu chuẩn thực tế cho REST API.

Sáu Ràng Buộc Kiến Trúc REST

1

Client-Server

Client và server tách biệt hoàn toàn — client không biết logic server, server không biết UI client. Điều này cho phép cả hai tiến hóa độc lập, tăng tính portable và scalability.

2

Stateless

Mỗi request từ client phải chứa đủ thông tin để server xử lý — server không lưu trạng thái client giữa các request. Session state được lưu hoàn toàn ở phía client (thường trong token). Điều này cải thiện visibility, reliability và scalability.

3

Cacheable

Response có thể được đánh dấu cacheable hoặc non-cacheable. Client và proxy có thể cache response cacheable, giảm tải server và cải thiện performance tổng thể.

4

Uniform Interface

Giao diện thống nhất qua toàn hệ thống: resource được xác định qua URI, thao tác trên representation (không phải resource gốc), message tự mô tả (self-descriptive), HATEOAS (hypermedia as engine of application state).

5

Layered System

Client không biết đang giao tiếp trực tiếp với server hay qua intermediary (proxy, load balancer, gateway). Các layer này có thể được thêm vào để improve scalability và security mà không ảnh hưởng giao diện.

6

Code on Demand (tùy chọn)

Server có thể gửi code thực thi (JavaScript, applet) về client khi cần. Đây là ràng buộc duy nhất không bắt buộc trong REST.

Tài Nguyên (Resource) — Khái Niệm Trung Tâm

Trong REST, tài nguyên (resource) là trừu tượng trung tâm — bất kỳ thứ gì có thể đặt tên: tài liệu, ảnh, bộ sưu tập dữ liệu, dịch vụ. Mỗi resource được xác định duy nhất bởi URI (Uniform Resource Identifier).

Client thao tác trên representation của resource (JSON/XML) — không phải resource thực tế. Server lưu resource theo cách riêng của nó, nhưng giao tiếp qua representation.

Đặt Tên URI — Quy Tắc Vàng

URI tốt là URI mô tả tài nguyên theo nghiệp vụ, không phải theo hành động. Quy tắc đặt tên:

Dùng danh từ số nhiều cho collection
/orders   /getOrders
Dùng kebab-case (gạch ngang) để phân tách từ
/order-items   /orderItems
Dùng chữ thường
/users   /Users
Phân cấp theo quan hệ cha-con
/customers/123/orders
Không dùng động từ trong URI
DELETE /orders/456   /deleteOrder/456
Không có dấu "/" cuối URI
/products/123   /products/123/

HTTP Methods — Hành Động Trên Resource

REST dùng HTTP method để thể hiện hành động. Mỗi method có ngữ nghĩa rõ ràng:

MethodCRUDIdempotentSafeMô tả & Ví dụ
GET Read✅✅ Lấy dữ liệu, không thay đổi server state. GET /products — lấy danh sách; GET /products/123 — lấy chi tiết.
POST Create❌❌ Tạo mới resource. POST /orders — tạo đơn hàng mới. Mỗi lần gọi tạo một resource mới.
PUT Update (full)✅❌ Thay thế hoàn toàn resource. PUT /customers/123 — ghi đè toàn bộ customer 123. Phải gửi đầy đủ representation.
PATCH Update (partial)✅*❌ Cập nhật một phần resource. PATCH /users/456 — chỉ cập nhật các field được gửi lên. Tiết kiệm bandwidth.
DELETE Delete✅❌ Xóa resource. DELETE /orders/789 — xóa đơn hàng 789. Gọi lần 2 vẫn trả về 404 (idempotent về kết quả).

HTTP Status Codes — Giao Tiếp Kết Quả

Status code chuẩn là cách API giao tiếp kết quả request với client. Sử dụng đúng status code giúp client xử lý phản hồi chính xác mà không cần phân tích body.

2xx — Thành Công

200
OK — Request thành công, response body chứa kết quả (GET, PUT, PATCH)
201
Created — Resource mới được tạo thành công (POST). Header Location chứa URI của resource mới.
204
No Content — Thành công nhưng không có body (DELETE, PUT khi không cần trả về)
206
Partial Content — Trả về một phần resource (phân trang, streaming)

4xx — Lỗi Client

400
Bad Request — Request sai cú pháp, tham số không hợp lệ, validation fail
401
Unauthorized — Chưa xác thực hoặc token không hợp lệ. Client cần đăng nhập lại.
403
Forbidden — Đã xác thực nhưng không có quyền truy cập resource này
404
Not Found — Resource không tồn tại hoặc đã bị xóa
409
Conflict — Conflict với state hiện tại của resource (duplicate key, optimistic lock fail)
422
Unprocessable Entity — Dữ liệu đúng cú pháp nhưng sai logic nghiệp vụ
429
Too Many Requests — Vượt rate limit. Header Retry-After cho biết khi nào có thể thử lại.

5xx — Lỗi Server

500
Internal Server Error — Lỗi không mong đợi ở server
503
Service Unavailable — Server tạm thời không phục vụ (maintenance, overload)
504
Gateway Timeout — Gateway không nhận được phản hồi từ upstream kịp thời

Phân Trang, Lọc & Sắp Xếp

Khi collection có nhiều item, cần cơ chế phân trang để tránh trả về toàn bộ dữ liệu một lần:

  • Offset-based pagination: GET /products?offset=20&limit=10 — đơn giản nhưng kém hiệu quả khi dữ liệu lớn
  • Cursor-based pagination: GET /products?after=cursor_xyz&limit=10 — hiệu quả hơn, dùng con trỏ vào vị trí cụ thể
  • Lọc (Filter): GET /orders?status=pending&customerId=cust-456
  • Sắp xếp (Sort): GET /products?sort=price&order=asc
  • Projection (chọn field): GET /users?fields=id,name,email — giảm bandwidth

HATEOAS — Hypermedia As The Engine of Application State

HATEOAS là ràng buộc cao nhất của REST (Level 3 trong Richardson Maturity Model). Mỗi response chứa links đến các hành động tiếp theo liên quan — giúp client khám phá API dynamically mà không cần biết trước toàn bộ URL structure. Xem ví dụ _links trong response ở trên.

Tuy HATEOAS là "pure REST", trong thực tế nhiều API chỉ đạt Level 2 (URI + HTTP Methods) vì HATEOAS phức tạp để implement và ít được client tận dụng đúng nghĩa. API level 2 vẫn được coi là "RESTful" trong ngành.

API Design Best Practices Tổng Hợp

  • Nhất quán — đặt tên, format, error structure phải nhất quán toàn bộ API
  • Consumer-first — thiết kế theo nhu cầu consumer, không theo cấu trúc database hay backend
  • Backward compatible — tránh breaking changes; dùng versioning khi bắt buộc thay đổi
  • Idempotent — PUT/DELETE phải idempotent; cân nhắc idempotency key cho POST
  • Validation sớm — validate ở gateway trước khi request đến backend
  • Security by design — HTTPS bắt buộc; không leak thông tin nội bộ trong error message
  • Tài liệu đầy đủ — OpenAPI spec đi kèm với mọi API thay đổi
