Các Mẫu Thiết Kế API

Facade, Aggregator, BFF và các pattern kiến trúc giải quyết thách thức thực tế

Tại Sao Cần API Patterns?

Trong quá trình xây dựng API cho hệ thống phức tạp, các vấn đề lặp đi lặp lại: backend quá chi tiết (chatty API), client quá phụ thuộc vào cấu trúc internal, cần tích hợp nhiều service khác nhau. API patterns là giải pháp đã được kiểm chứng để giải quyết các thách thức này một cách có cấu trúc.

1. Facade Pattern (Mặt Tiền)

Abstraction Simplification Decoupling

Facade tạo ra một giao diện đơn giản hóa che giấu sự phức tạp của hệ thống phía sau. Client tương tác với Facade thay vì trực tiếp với các subsystem phức tạp.

Client App → [ Facade API ] → Subsystem A
↘ Subsystem B
↘ Subsystem C (Legacy)

Ứng dụng trong API: Khi backend là hệ thống legacy phức tạp, API gateway tạo ra Facade RESTful hiện đại bên trên. Client không cần biết backend dùng SOAP, CORBA hay cấu trúc database như thế nào.

Ví dụ thực tế: Một ngân hàng có core banking system 30 năm tuổi. Thay vì để fintech partner tích hợp trực tiếp với SOAP service cũ, họ xây Facade API RESTful/JSON hiện đại bên trên — đơn giản hóa tích hợp và che giấu complexity nội bộ.
✅ Lợi ích
  • Đơn giản hóa giao diện cho consumer
  • Backend tự do thay đổi implementation
  • Giảm coupling giữa client và backend
❌ Lưu ý
  • Facade có thể trở thành bottleneck
  • Cần maintain cả Facade lẫn backend
  • Abstraction layer thêm latency nhỏ

2. Aggregator Pattern (Tổng Hợp)

Composition Microservices Reduce Round-trips

Aggregator nhận một request từ client, gọi nhiều downstream API/service, tổng hợp kết quả và trả về một response duy nhất. Giải quyết vấn đề "chatty" — client phải gọi quá nhiều API để lấy đủ dữ liệu cần.

Client → [ Aggregator ] → Product Service
↘ Inventory Service
↘ Review Service
↘ Pricing Service
← [ Tổng hợp kết quả ]

Hai loại aggregation:

  • Sequential — gọi service theo thứ tự, output của service này là input của service tiếp theo
  • Parallel — gọi tất cả service đồng thời, tổng hợp kết quả sau. Giảm latency tổng thể.
Ví dụ thực tế: Trang product detail của Amazon gọi hàng chục microservice song song: product info, inventory, reviews, recommendations, seller info, shipping options — tất cả được aggregated thành một response duy nhất cho browser.
✅ Lợi ích
  • Giảm số round-trips từ client
  • Client code đơn giản hơn
  • Parallel call giảm latency
❌ Lưu ý
  • Aggregator phức tạp, khó test
  • Partial failure handling khó
  • Circuit breaker cần thiết

3. Backend for Frontend (BFF) Pattern

Multi-client Optimization Experience API

BFF tạo ra một API backend riêng biệt cho mỗi loại client (mobile, web, TV, partner). Thay vì một API chung phải đáp ứng nhu cầu của tất cả client, mỗi client có API được tối ưu riêng cho nhu cầu của nó.

Mobile App → [ Mobile BFF ] ↘
Web Browser → [ Web BFF ] → Backend Services
3rd Party → [ Partner BFF ] ↗

Tại sao cần BFF? Mobile app cần data ít hơn web (bandwidth hạn chế), cần cấu trúc dữ liệu khác (flat cho list view), cần cache strategy khác. Nếu dùng chung API, sẽ luôn over-fetch hoặc under-fetch với ít nhất một loại client.

Ví dụ thực tế: Netflix có BFF riêng cho smart TV, iOS, Android, web browser — mỗi BFF tối ưu dữ liệu và format cho khả năng render của từng thiết bị, giảm bandwidth và cải thiện UX.
✅ Lợi ích
  • API tối ưu cho từng client
  • Team frontend tự chủ BFF của mình
  • Giảm over/under-fetching
❌ Lưu ý
  • Nhiều BFF = nhiều code trùng lặp
  • Cần maintain nhiều service
  • Phù hợp khi client có nhu cầu thực sự khác nhau

4. Gateway Pattern

Single Entry Point Cross-cutting Concerns Microservices

API Gateway là điểm vào duy nhất cho tất cả client request, xử lý cross-cutting concerns (auth, rate limiting, logging, SSL termination) tập trung thay vì implement ở từng service.

Gateway tách biệt hai loại concern: north-south traffic (client ↔ API, cần auth, rate limiting nặng) và east-west traffic (service ↔ service nội bộ, cần discovery, circuit breaking). Nhiều tổ chức dùng service mesh (Istio, Linkerd) cho east-west và API gateway cho north-south.

Ví dụ thực tế: AWS API Gateway xử lý auth, throttling, caching, logging cho tất cả service của một doanh nghiệp — các Lambda function backend chỉ cần focus vào business logic.

5. Proxy Pattern

Mediation Legacy Integration Protocol Translation

API Proxy đứng giữa client và backend service, forwarding request và response với (hoặc không có) transformation. Cho phép thêm capabilities (auth, logging, rate limiting) vào existing service mà không cần thay đổi service đó.

Reverse Proxy vs Forward Proxy: Reverse proxy (NGINX, Apache) bảo vệ backend từ client. Forward proxy bảo vệ client khi truy cập internet. API proxy thường là reverse proxy với thêm API management capabilities.

6. Circuit Breaker Pattern

Resilience Fault Tolerance Microservices

Khi một downstream service fail liên tục, Circuit Breaker "ngắt mạch" — dừng gọi service đó trong thời gian ngắn, trả về fallback response ngay lập tức. Ngăn cascade failure (lỗi lan rộng qua toàn hệ thống).

Ba trạng thái: Closed (bình thường, cho phép request qua), Open (đã ngắt, block request, trả fallback ngay), Half-Open (thử lại một số request để kiểm tra service đã phục hồi chưa).

Netflix Hystrix (sau này là Resilience4j) là implementation Circuit Breaker nổi tiếng nhất, được Netflix dùng để đảm bảo trải nghiệm streaming luôn hoạt động kể cả khi một số microservice gặp sự cố.

7. Retry Pattern với Exponential Backoff

Resilience Transient Failures

Tự động retry request khi gặp lỗi tạm thời (network blip, service restart). Kết hợp với Exponential Backoff — tăng thời gian chờ theo cấp số nhân sau mỗi lần retry — để tránh "thundering herd" (tất cả client retry cùng lúc làm sập server đang hồi phục).

Chỉ retry với idempotent operations (GET, PUT, DELETE). Không retry POST (có thể tạo duplicate). Thêm Jitter (ngẫu nhiên hóa thời gian retry) để phân tán load.

Chọn Pattern Phù Hợp

Không có pattern nào phù hợp cho mọi tình huống. Nguyên tắc chọn lựa:

  • Nhiều client với nhu cầu khác nhau → BFF
  • Nhiều microservice, client cần tổng hợp → Aggregator
  • Backend legacy, cần modern interface → Facade
  • Cần một điểm vào tập trung → Gateway
  • Hệ thống cần resilient → Circuit Breaker + Retry + Timeout kết hợp

Trong thực tế, các pattern thường được kết hợp: Gateway + BFF + Circuit Breaker là bộ ba phổ biến trong kiến trúc microservices hiện đại.
